# 0004 · 拨测的报警器必须与拨测不在同一个失效域

状态：生效（2026-09-29）

## 背景

`nightly-status.yml` 是「从 GitHub 网络位置看你的服务器还在不在」的最后一环。它先后两次以同
一种难看的方式失败：先是三个 action 钉版全是查无此 commit 的值（job 起不来），修好之后又死在
pnpm/action-setup 的版本冲突上。两次都**没有任何 issue 被创建**——因为「失败就开 issue」的步骤
和拨测本身在同一个 job 里，job 起不来时那条步骤根本不会执行。

## 决策

- 拆成 `probe`（跑与判红，产物上传 artifact）与 `report`（`needs: probe` + `if: failure()`，专职开单）。
- `report` 拿不到 `probe.json` 时**照样开单**，正文明确写「探针未执行完成，这既不是线上正常也
  不是线上挂了，而是哨兵自己没站起来」。
- `report` 不 checkout 仓库，只依赖 runner 自带的 `gh`，减少自身失效面。

## 后果

- 「静默没跑」变成可见事件。代价是一次故障可能开出并非线上问题的 issue（需要人读正文判断）——
  这是正确的方向：误报可接受，漏报不可接受。
- 立了一条通用规矩：**任何监控系统，没被人为制造过一次失败并观察到告警到达，就不算存在**。
  本次以一次性演练分支验证（把已知故障装回去 → 确认开单 → 绿色运行自动关单），之后删除分支。
- 同类待查：只在 tag / 特定条件下跑的 workflow 仍缺这条「它自己能不能启动」的断言。

证据：`.github/workflows/nightly-status.yml` 头部注释、issue #14（演练产物，已自动关闭）。
